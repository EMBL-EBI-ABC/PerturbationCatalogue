# Review notes — comparison against Wainberg et al. (kundajelab/coessentiality)

Tracking review feedback on [PR #365](https://github.com/EMBL-EBI-ABC/PerturbationCatalogue/pull/365)
(reviewer: @tskir), including comparisons to the original
[kundajelab/coessentiality](https://github.com/kundajelab/coessentiality) codebase
and the [Wainberg et al. 2021 Nature Genetics paper](https://pmc.ncbi.nlm.nih.gov/articles/PMC8763319/).

## Comment 1 — Olfactory receptor PCA bias correction (`load_screens.py`)

**Reviewer's comment:** The original `load_screens.py` does sample preprocessing,
a PCA-based bias correction using olfactory receptor (OR) genes as negative
controls, then a PCA transformation. This repo's pipeline does not replicate
that step. Is it needed?

**Findings:**
- Original logic: fits a 4-component PCA on OR-gene effect profiles only (OR genes
  are non-functional outside olfactory neurons, so any structured signal in their
  profiles is treated as technical noise — a RUV-style negative-control correction).
  Projects the *entire* gene matrix onto those 4 components and subtracts the
  reconstruction from every gene. This was needed in 2021 because CERES (the
  gene-effect model DepMap used then) didn't fully remove screen-quality/batch
  variation on its own.
- Current pipeline ([step1_fetch_depmap.py](pipeline/step1_fetch_depmap.py)) downloads
  DepMap's official `CRISPRGeneEffect.csv`, which is generated by **CHRONOS**
  (Dempster et al. 2021). CHRONOS's mechanistic model explicitly targets sgRNA
  efficacy, variable screen quality/growth rate, and heterogeneous cutting outcomes,
  plus a separate post-hoc copy-number-bias spline correction.
- Conclusion: the OR-PCA correction is very likely redundant on top of
  Chronos-corrected input data — replicating it risks removing real signal rather
  than residual noise.

**Decision:** Not replicated. No code change.

**Status:** Resolved (no action) — pending: add a short note to README explaining
why this step was intentionally omitted, so it isn't re-raised in future reviews.

## Comment 2 — Global vs. per-gene FDR correction (`step3_fdr_coessentiality.py`)

**Reviewer's comment:** This pipeline applies Benjamini-Hochberg FDR correction
globally across all gene pairs, but Wainberg's supplementary description refers
to "10% per-gene FDR." Is this intentional?

**Findings:**
- Wainberg's Methods: *"Benjamini–Hochberg FDR correction was performed for each
  gene across its 17,633 partners"* — a **per-gene (row-wise)** correction, not a
  single genome-wide correction. Our code instead stacks all unique pairs into one
  array and applies a single **global** BH correction across ~160M pairs
  ([step3_fdr_coessentiality.py:55-82](pipeline/step3_fdr_coessentiality.py#L55-L82)).
- Empirically (on `depmap_26Q1_GLS_p.npy`, 17,870 genes, ~160M pairs, FDR ≤ 10%):
  global finds 29,654 significant pairs vs. ~44,546 for per-gene — a real
  discrepancy (~63% overlap), not a rounding difference.
- **Why Wainberg used per-gene FDR:** the paper states no rationale for this
  choice anywhere in the Methods — checked and confirmed not established.
- **Why we keep global FDR — global preserves the strongest co-essential pairs.**
  Validated empirically: of the 15,772 pairs that pass per-gene-OR but fail global,
  their global-adjusted p-values range 0.10-0.43 (median 0.173) — i.e., every pair
  global correction *does* keep is stronger than every one of those. Because global
  correction divides by a much larger denominator (~160M vs. ~17,870 per row), only
  the most statistically robust signals in the dataset survive it. Per-gene FDR also
  has no defined rule for symmetrizing a pair when the two genes' rows disagree, so
  it only controls a per-row error rate, not a real pair-level FDR. Global gives one
  well-defined, symmetric per-pair FDR and keeps only the strongest signals — the
  right guarantee for what we report as a general-purpose network.

**Decision:** Keep **global BH correction** in `step3_fdr_coessentiality.py`. This
intentionally diverges from Wainberg's per-gene FDR; the rationale is documented
above. No code change required.

**Correction (post-resolution follow-up):** We later checked the actual
kundajelab/coessentiality GitHub code to see whether Wainberg's real
implementation matches the paper's "per-gene FDR" claim. `modules.py` does apply
BH correction **globally** (one `fdrcorrection()` call across all stacked unique
pairs) — but on closer inspection, that computation produces **ClusterONE edge
weights for module/cluster detection**, a different downstream artifact from the
**pairwise significant-partners network** (each gene's partner list at 10% FDR,
presumably the basis for the published 93,575-pair count). No script in the
public repo computes that second, pairwise network at all — so there is **no
verifiable code for the per-gene FDR claim, but also no verifiable code that
validates our global choice against Wainberg's actual pairwise-network method
either.** The global-FDR-for-clustering-weights finding doesn't transfer to the
pairwise-network question; our decision to use global rests on our own
statistical reasoning (a well-defined, symmetric per-pair FDR guarantee — see
above), not on matching or contradicting Wainberg's unpublished implementation.

**Numbers update:** the 29,654 / 44,546 figures above were computed on the
pre-Comment-5 dataset (17,870 genes, before the NA-imputation bug fix). On the
corrected 26Q1 data (17,087 genes, ~146M pairs): **global = 25,889**,
per-gene-AND = 27,346, per-gene-OR = 40,081. Same qualitative pattern holds.

**Status:** Resolved — pending: add a short note to README's FDR section
cross-referencing this decision, so future reviewers comparing pair counts to the
published ~93,575-pair network (or coessentiality.net) understand why ours differs.

## Comment 3 — `corr_genes` field is a sign, not a correlation (`step2_gls_coessentiality.py:146`)

**Reviewer's comment:** Here, the pipeline saves only `np.sign(GLS_coef)`, without
saving the coefficient itself. But downstream code calls this value "correlation",
which it isn't (it's a sign/direction). This loses magnitude and makes the app show
values like 1.000 / -1.000, which users may read as actual correlation coefficients
and assume "perfect correlation". As a minimum, this field needs to be renamed (here
& downstream, including the UI). But potentially even more significantly, we need to
think about whether we *should* be losing magnitude information. This seems
potentially useful. Probably something that you can discuss with @AleksZakirov.

**Decision:** Renamed `corr_genes` → `direction` everywhere (pipeline output column,
app code/UI labels, README, workflow docs, and the existing
`depmap_26Q1_gls_whole_coessential_network_FDR_10.csv` data file — header only,
values unchanged). Magnitude (saving the actual `GLS_coef` instead of just its
sign) was scoped out of this fix.

**Status:** Resolved. Naming fixed; on the magnitude question, agreed (👍 on
the PR thread) with Aleks's input below that there's no single well-defined
magnitude to store without picking an arbitrary directional convention —
not pursuing further.

**@AleksZakirov's input (2026-06-18):** Pointed to the paper's Methods, verified
verbatim: *"although the GLS P value is consistent regardless of which of the two
genes is chosen as endog and which as exog, the GLS effect size is not consistent
with respect to this choice, and as a result is not reported."* In other words,
the GLS coefficient for pair (A,B) depends on which gene is treated as the
predictor vs. the response — regressing A on B gives a different coefficient than
regressing B on A (only the **sign** is guaranteed to match between the two
directions, not the magnitude). This is why Wainberg's paper never reports an
effect size at all, only the p-value and sign.

**Implication for the magnitude decision:** this isn't just "should we store more
data" — there's no single, well-defined magnitude value per gene pair to store in
the first place without picking an arbitrary convention (e.g., always use the
alphabetically-first gene as predictor, average the two directions' coefficients,
or report both). Whatever Aleks/the team decides here also has to settle that
convention question, not just whether magnitude is "useful."

## Comment 4 — Missing pipeline validation / benchmarking (`README.md:25`)

**Reviewer's comment:** General point: I think one important step / component which
is missing almost completely here is validation. While it's true that we're basing
the prototype on good quality data (DepMap) and good quality approach (Wainberg
2021), the actual implementation is our own and quite detailed / complicated. We
want to be able to say "Yep, after we run this pipeline, it produces sensible
results" and also we want to be able to vary some parameters of the pipeline and see
if it performs better or worse. So we need *some* sort of benchmark which takes
pipeline results as input and produces a numerical metric, or better yet a set of
metrics, which we can then compare. I think this might be a good item to be
brainstormed with an agent, and also discussed with @AleksZakirov.

**Analysis:** "Vary parameters and see if it performs better or worse" needs a
yardstick — a purely computational check can confirm the code *ran correctly*, but
not whether one parameter choice is *more biologically sensible* than another. That
requires comparing against an external ground truth. So this splits into two
layers, both worth doing:

1. **Computational/sanity layer (cheap, no external data needed):**
   - Check output matrix shapes/symmetry and that no NaNs/Infs silently propagate.
   - Permutation check: shuffle cell-line labels (destroying real gene-gene
     relationships) and confirm the GLS p-value histogram comes out flat/uniform —
     this confirms the test isn't structurally biased toward false positives.
   - A small hand-built synthetic example (5-10 genes with known
     correlated/uncorrelated profiles) where the correct significant pairs and
     signs are known in advance — confirms the pipeline recovers them.
   - Cheap enough to run as a fast test suite on every pipeline change.

2. **Biological/functional layer (the actual "better or worse" yardstick):**
   - Download CORUM (protein complexes) and/or STRING (functional interactions) as
     gold-standard positive pairs — both freely available.
   - Score our network against them with one simple metric: precision/recall (or
     AUPRC) of how well our significant pairs — or the raw GLS p-value ranking —
     recover known CORUM/STRING pairs.
   - Re-run Wainberg's GLS-vs-Pearson comparison on our own implementation and
     current Chronos-corrected data — not to find anything new (Wainberg already
     showed GLS wins), but as a regression check that our implementation reproduces
     the expected result, and it gives Comment 1's decision (skip OR-bias
     correction) real empirical backing instead of resting on documentation alone.
   - The same metric can then be reused to A/B any future parameter choice (NA
     imputation strategy from Comment 5, FDR rule from Comment 2, etc.) instead of
     reasoning about each in isolation.

**Status:** Resolved — CORUM+GLS validation implemented and produces a sane
result (see below), with a side-by-side comparison against Wainberg et al.'s
own published CORUM number added on top. STRING/hu.MAP/DoRothEA and the
Pearson/bias-correction comparison deliberately **not** pursued — see
"Closing this out" below for why.

**@AleksZakirov's input (2026-06-18):** Pointed out the paper already did
extensive benchmarking — Figure 2 and Extended Data Figure 4 ("GLS improves
recall of known functional interactions in co-essential gene pairs and modules,"
with/without PCA-based bias correction). Suggested replicating some of these
validations as a useful sanity check — directly confirming the biological/
functional layer (option 2) above, and Extended Data Fig 4 in particular is
specifically the GLS-with/without-bias-correction comparison that would give
Comment 1's decision real empirical backing. Next step: look at exactly what
gold-standard data and metric those figures used, to replicate as closely as
practical rather than inventing our own from scratch.

**Implemented (MVP, scoped to CORUM + GLS only):** Checked exactly what Fig 2 /
Ext Data Fig 4 measure — gold standards CORUM/hu.MAP/STRING (co-expression-only
pairs removed)/DoRothEA; metric is "enrichment" = (% of top-N pairs found in the
gold-standard database) / (% of all possible pairs found in it); x-axis is top-N
partner ranks per gene (N=1..10); methods compared include GLS with/without bias
correction and Pearson with/without bias correction.

Built a standalone maintainer tool in `pipeline_validation_corum/` (new folder,
deliberately kept separate from the production pipeline since this is a
one-off sanity check, not a monthly pipeline step or a CI-wired regression
test): CORUM gold standard (fetched via `gseapy.get_library(name="CORUM")` —
same Enrichr mechanism as the GO:BP fix in Comment 10, 1,658 human complexes,
gene-symbol-native so no ID-mapping needed), evaluated against GLS only (no
Pearson comparison). Built as `corum_validation.ipynb` — an interactive
notebook (rather than a plain script) so anyone re-running it can see the
head samples of both raw inputs, the CORUM-to-pairwise processing step with a
worked example, and the results table/plot directly.

**Result** (full table, mermaid flowchart, and interpretation in
`pipeline_validation_corum/RESULTS.md`): across 2,284 genes with ≥1 CORUM
complex-mate in our 17,087-gene panel, GLS's top-1 ranked partner is the
gene's *actual* CORUM complex-mate 26.9% of the time, vs. a 0.016% background
rate — **~1,658x enrichment over chance at N=1** (Fisher's exact p < 1e-300),
declining smoothly to ~723x at N=10. Sane, expected pattern (best-ranked
prediction more reliable than 10th-best), and consistent with the literature
finding that complex membership is one of the strongest co-essentiality signals.
**Directly answers "does this pipeline produce sensible results?" — yes.**

**Closing this out — comparison with Wainberg et al., and why STRING/hu.MAP/
DoRothEA/Pearson weren't pursued:** Added a side-by-side comparison against the
paper's own published CORUM number (~160-fold enrichment vs. our ~1,658-fold —
see RESULTS.md for the full discussion of why these aren't perfectly
apples-to-apples, e.g. more cell lines in 26Q1, Chronos vs. CERES). On the
OR-bias/Pearson comparison specifically: the paper states GLS "automatically
performs bias correction without requiring a putatively nonessential gene set
like olfactory receptors" — i.e. Wainberg et al. already established this for
GLS specifically, so re-deriving it ourselves via a Pearson comparison would
be re-proving a settled finding, not adding new information. Decided CORUM
alone is sufficient as the one validation gate; the other gold standards
(STRING/hu.MAP/DoRothEA) were not pursued, as CORUM was judged sufficient to
answer the core question. Replied on the PR thread with the final result.

## Comment 5 — Ad hoc NA imputation strategy (`step2_gls_coessentiality.py:53`)

**Reviewer's comment:** The missing-value strategy is a bit ad hoc: genes with NA
counts at or below the median are median-imputed, the rest are dropped. Not saying
it's bad, but it changes covariance structure and pairwise p-values and therefore
needs validation. This connects to above comment I made about validation for the
pipeline in general.

**Findings:** Checked against the live `CRISPRGeneEffect_26Q1.csv` — the "ad hoc"
threshold was worse than it looked. The median-of-NA-counts cutoff worked out to
**825 missing cell lines = 68.3% missing**, meaning 783 genes were having up to 68%
of their profile filled in with a single constant (their own median) before every
pairwise GLS p-value involving them was computed. This wasn't dead/unused code —
the production data (`depmap_26Q1_genes.txt` etc.) was generated with this path
active (1,444 genes had NAs; 661 dropped, 783 imputed under the 68.3% threshold —
matches the live 17,870-gene file exactly: 18,531 − 661 = 17,870).
This logic turned out to be left over from an unrelated prior BioGRID-data
experiment and was never meant to be part of this pipeline.

**Decision:** Removed entirely. `step2_gls_coessentiality.py` now unconditionally
drops every gene with any NA (no imputation, no `--no-impute` flag, no threshold).
On `CRISPRGeneEffect_26Q1.csv` this leaves **17,087 genes** (vs. 17,870 before).
README and CLI usage text updated to match.

**Status:** Resolved (code). Data regeneration in progress — step2 (GLS
computation, ~4-8h) launched in background to rebuild `depmap_26Q1_genes.txt`,
`depmap_26Q1_GLS_p.npy`, `depmap_26Q1_GLS_sign.npy`; step3 (FDR network CSV) to
follow once step2 completes. **Pending: re-run step3 and verify the FDR ≤10%
pair count after regeneration** (current 29,654-pair figure used in Comment 2 was
computed on the old, imputed gene set and will change slightly).

## Comment 9 — Non-deterministic truncation when expanding gene-list network (`app/coessentiality_feature_pc.py:284`)

**Reviewer's comment:** `list(new_genes)[:room]` is non-deterministic, because set
to list conversion is non-deterministic, which is not ideal. But I think a bigger
issue is that we're truncating the list to the ~random 300 genes. Is there a better
way to truncate a very large network? Could we use abs(GLS coefficient) as an effect
size perhaps, and filter on that? Or on combination of that and p-value? One more
thing to probably discuss with @AleksZakirov.

**Analysis:** Two separate problems, not an efficiency issue — `list(new_genes)[:room]`
truncates a Python `set`, whose iteration order depends on string hash randomization
(different per process), so the same query can return different surviving genes
across app restarts. Separately, even with stable ordering, picking "whichever genes
happen to come first" has no biological rationale.

**Options:**
- **A — Deterministic but still arbitrary (quick).** `sorted(new_genes)[:room]`
  (alphabetical). Fixes the non-determinism bug in one line; doesn't fix the
  "no principled reason" problem.
- **B — Rank by p-value (implementable now, no pipeline change).** For each
  candidate gene, take the best (smallest) adjusted p-value among its edges into
  the current network; sort ascending; keep top `room`. Deterministic and
  principled, using the `pvalue_adj` column we already have.
- **C — Rank by effect size `abs(GLS coefficient)` (the reviewer's actual ask) —
  blocked.** Requires preserving coefficient magnitude, which is exactly Comment
  3's open scope (we currently only store `direction`, ±1). Once resolved, this
  becomes the better version of B (rank by effect size, tie-break by p-value).
- **D — Surface the truncation in the UI (orthogonal to A/B/C).** Whatever
  ranking is used, tell the user e.g. "847 genes found at degree 3; showing the
  top 300 by significance" — currently the cap is silent.
- **Recommendation:** ship B now (cheap, fixes the real bug, no new data needed);
  revisit C once Comment 3's magnitude question is settled — they're naturally
  sequenced, not competing. D is worth doing regardless of ranking choice.

**@AleksZakirov's input (2026-06-18):** Asked directly — "Is there a problem with
using more than 300 nodes in the network (apart from visibility, of course)?"
Checked the codebase: `MULTI_MAX_EXPANDED_GENES = 300` is only ever justified in
comments/docs as "so the layout stays readable and the callback stays fast" — no
measured Cytoscape.js rendering benchmark or callback-latency threshold exists
anywhere backing the specific number 300. **This is an open question for us to
answer, not yet resolved** — either point to an actual measured limit (e.g. test
Cytoscape.js rendering/interaction performance at 500/1000+ nodes, or time the
callback at larger sizes) or concede there's no hard technical reason and the cap
could be raised or made configurable.

**Aleks's follow-up (2026-06-19):** Proposed a concrete plan — rank pairs by
p-value (no sign-stratification), raise the cap to something Cytoscape-safe,
truncate by p-value if still over, and show a "truncated for performance" message.

**Real-world confirmation:** generated 10,000 random HGNC protein-coding gene
symbols and pasted them into the app to stress-test it — **it crashed**. The
backend process stayed alive and error-free throughout (confirmed via logs/HTTP
checks), so the crash was on the frontend (Cytoscape trying to render the
network), not a Python exception. This also exposed a second, more direct bug:
**the cap only ever applied during degree-of-interaction expansion** — pasting a
huge list directly with the slider at 0 went straight to Cytoscape completely
uncapped. Of the 10,000 pasted genes, 8,756 matched the DepMap panel; even after
filtering to *only* FDR≤10% significant pairs among them (no cap at all), the
induced sub-network was still 5,380 genes / 7,165 pairs — confirming a hard
cap is still necessary even with significance filtering, since "significant"
does not mean "small" for a large, well-connected input set. Also tested and
ruled out a percentage-based cap (e.g. "keep top 25%") — it would over-truncate
small/normal networks that are already safe to render while still not
guaranteeing safety for huge ones; an absolute ceiling, applied only when
exceeded, is the right mechanism.

**Decision:** Implemented Aleks's plan, extended to cover both cases:
- New `_truncate_genes_by_significance()` helper: ranks genes by their best
  (smallest) adjusted p-value within the candidate set, deterministically keeps
  the top N up to the cap (no more hash-order randomness), with any remaining
  room filled by leftover/isolated genes in alphabetical order.
- Applied to the **raw pasted gene set itself**, before any expansion — fixes
  the crash directly.
- Applied inside `_expand_by_degree()`, replacing `list(new_genes)[:room]` with
  the same significance-ranking logic (the original non-determinism complaint).
- `MULTI_MAX_EXPANDED_GENES` raised from 300 to **500** (no browser-testing
  tooling available to find an exact safe ceiling; this is a starting point for
  further manual testing, not a measured limit).
- Added a visible message whenever truncation fires: "Network truncated to the
  500 most statistically significant genes (sorted by GLS p-value) to preserve
  performance."
- The "Download pairs (CSV)" button applies the same truncation, so downloads
  match what's displayed.
- Removed the "Not found in network: gene1, gene2, ..." list from the summary
  for this view — not informative at scale (e.g. listing the first 10 of 1,244
  unmatched genes from a 10,000-gene paste); the equivalent message for the
  separate "fewer than 2 valid genes" error case was left unchanged since it's
  still useful there (small lists, likely typos).

**Status:** Resolved. Re-tested live with the same 10,000-gene file after the
fix — confirmed working (no crash, cap and message behave as expected).
Replied on the PR thread.

## Comment 10 — Enrichr dependency for GO enrichment (`app/coessentiality_feature_pc.py:1201`)

**Reviewer's comment:** We should migrate this so that enrichment is performed
locally, with no requests being sent to Enrichr. This is primarily because we don't
want to rely on their service availability and bandwidth.

**Findings:** gseapy (already a dependency) has a built-in local mode —
`gp.enrich()` — that runs the same hypergeometric test offline against a custom
gene-set library (dict or `.gmt` file) plus an explicit background, returning the
same result schema (`Term`/`P-value`/`Adjusted P-value`/`Genes`) as the old
`gp.enrichr()`. Confirmed Enrichr's GO:BP library is versioned infrequently
(currently offers 2021/2023/2025/2026 — roughly every 1-2 years), so pinning a
local copy doesn't sacrifice freshness in practice. Fetched and verified the actual
file: `GO_Biological_Process_2025.gmt` is **~1.4 MB**, 5,341 terms, downloaded once
in under 2 seconds.

**Decision:**
- Downloaded the library once via `gp.get_library(name="GO_Biological_Process_2025",
  organism="Human", save="required_data/GO_Biological_Process_2025.gmt")` — pinned,
  not auto-refreshed; bump deliberately when a meaningfully newer version matters.
- App loads it once at startup into `_GO_LIBRARY` (module-level, same pattern as
